# Verify Feedmark

Push CI invokes `python tools/verify-feedmark.py <run> --build-only`, retaining `buildAccepted` separately from `nativeAcceptance=false`. Manual workflow dispatch with `drive_native=true` first runs that same test plan with `--stage-build`, then drives the staged app in a separate job with `--native-from <artifact-dir>`. A skipped native path is not a passing native check. Both jobs restore the fixture, shut down their owned simulator and retain evidence.

Baseline proven on hosted run [39508929461](https://github.com/STEVVVU/feedmark-ios/actions/runs/39508929461), source `d5f728b92`. The unsigned app built, five existing iOS tests passed, the warning gate passed, and the real native reading flow passed. The downloaded article screenshot was inspected; RSS requests and all four cleanup flags were checked after shutdown. No local Xcode or iOS simulator is installed on the Windows workspace. Newly added annotation paths require their own proof.

## Launch

Use the `Feedmark checks` workflow on branch `feedmark`. Its maintained driver is `tools/verify-feedmark.py`. It refuses execution outside a dedicated macOS GitHub runner. Xcode 26.3, the iPhone 17 device type and an installed iOS runtime matching the active simulator SDK's major/minor version must already exist. The build and native jobs each create an owned simulator. The native job depends on the successful build job and downloads its same-run staged app. Separate hosts are an unproven resource-isolation experiment. The driver never resets a user's simulator, accepts no Xcode terms and uses the upstream unsigned simulator configuration. No developer account or provisioning update is used.

The build job runs the upstream iOS test plan. For this isolated build only, it replaces the bundled default feed list with a loopback synthetic RSS source and restores the original bytes during cleanup. The app is archived with macOS `ditto`; a manifest records the source commit, run and producing attempt, archive and executable hashes, executable mode, and fixture port and hash. Artifact names include the producing attempt; a rerun of the native job uses the build job's recorded artifact and attempt. The native job validates the successful build receipt, archive paths, hashes and restored executable mode, then binds the exact nonprivileged port; an occupied port fails the run. The archive protocol rejects all symlinks. If the real app bundle requires them, the hosted run will fail and the protocol must be reconsidered. The hosted run must establish that the archive actually preserves the executable metadata. This is verification input, not a replacement product feed list. Service API-key environment variables are removed before generating the upstream Secrets source. The test fixture uses the normal local-feed account and reader path.

The former combined job had a 45-minute workflow ceiling. Each of the two sequential jobs now has its own 45-minute ceiling, for a possible 90 minutes combined; existing individual command and native assertions retain their bounds.

## Doctor

Capture host architecture, CPU count and memory, Xcode/Java versions, simulator inventory, simulator UDIDs/runtime, stage timings and build/test logs. The test target uses the built app as its host. For a native drive, install the same build on the fresh simulator and compare its bundle identifier, executable name and executable SHA-256 with the built app; retain both paths and hashes in `installed-app.json`. Missing or mismatched installations fail the run. Runs 41413820454 and 41416407331 timed out on different simulator commands after XCTest. The latter subsequently retrieved the data container and app logs, so the cause is unknown. Run 41418998833 installed and drove the reader and notebook on an arm64 simulator; run 41423747227 timed out installing on its fresh simulator. GitHub maps `macos-26` to [arm64](https://github.com/actions/runner-images) and lists [Xcode 26.3 on that image](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md). Do not infer a working simulator from a workflow dispatch. A missing runtime, unaccepted setup, compilation error or native driver failure keeps onboarding a draft.

Compiler investigation retains `-Xfrontend -debug-time-function-bodies` output in `build.log`, captures the installed frontend's hidden help in `compiler-options.log`, and writes built-in `-stats-output-dir`, `-fine-grained-timers` and `-profile-stats-entities` results under `compiler-evidence/`. The existing artifact pattern retains that entire directory. In [Swift 6.2.4's function request](https://github.com/swiftlang/swift/blob/swift-6.2.4-RELEASE/lib/Sema/TypeCheckStmt.cpp), the timer includes pre-checking, scope expansion, statement checking, diagnostics, actor isolation and effects, using user plus system process CPU time. The [compiler options](https://github.com/swiftlang/swift/blob/swift-6.2.4-RELEASE/include/swift/Option/Options.td) and [statistics reporter](https://github.com/swiftlang/swift/blob/swift-6.2.4-RELEASE/lib/Basic/Statistic.cpp) define entity profiles including process and wall time. Inspect actual support, files, source entities and coverage before attributing a cause. Missing spans or profiles remain an unproven diagnostic. The expression-only dump is removed to reduce verbose instrumentation; all original warning gates and checks remain. Nested intervals overlap and instrumentation adds work, so these results are not optimization-gain measurements.

On an installation timeout, the driver records a diagnostic-only app-container lookup and binary identity/mode if accessible, then captures host CoreSimulator/client and owned-simulator installation-service logs. Lookup and each log command retain their existing 30-second bound; errors are recorded in `result.json`. The original installation timeout remains a failure even if the app appears afterward. These diagnostics have focused local tests but still need hosted execution. They use the existing command/log tooling, following Apple's [simulator command reference](https://developer.apple.com/documentation/xcode/xcode-command-line-tool-reference) and [guidance to retain simulator diagnostics rather than erase devices](https://developer.apple.com/forums/thread/762949); the forum's unrelated cloning bug is not diagnosed here.

## Drive

Maestro CLI 2.11.0 is a test-only tool, downloaded from its official GitHub release and verified against SHA256 `5384593cb4e7a106489e75a821d157dd43f4e438df6bc308b72e82c685e1283a`. It is Apache-2.0 licensed. Run only against the created simulator. Analytics and update checks are disabled; no cloud or AI command is invoked. All requested app permissions are denied explicitly.

The generated baseline flow selects `Feedmark verification feed`, opens `Evidence survives the network` and verifies the synthetic article text. The driver also verifies that the actual app fetched `/feed.xml`. The original baseline retained an explicit article PNG; subsequent runs set Maestro's actual `--test-output-dir` so the requested sidebar/timeline/notebook PNGs are also uploaded. See [the feature map](features/README.md). Existing iOS unit tests are additional evidence, not a substitute for this native path.

The next run uses one Maestro CLI session with ordered `runFlow` subflows and loopback callbacks that perform the real host-side checks and fixture changes. Run39520091249 provides actual save/relaunch proof but does not clear its failed mutation step. No collaboration feature is implemented.

## Cleanup

Restore the original OPML bytes, shut down only the created simulator UDID and close the owned loopback RSS server in each job. Retain the simulator profile, all evidence and logs until the hosted job ends. The driver does not delete user profiles or stop unrelated simulators. Confirm shutdown, fixture restoration and evidence retention in each `result.json` after failures as well as success. GitHub's [artifact actions](https://github.com/actions/upload-artifact#permission-loss) do not retain uploaded file permissions, so the app is transferred as an archive rather than as loose files; the native job checks its restored executable mode.
